Interpretation on these results:
The Baseline Drop: The execution time drops massively from -O0 to -O1 because fundamental optimizations (like holding variables in CPU registers instead of constantly fetching from memory) are applied.

The Plateau: The times for -O2 and -O3 are nearly identical. The compiler has exhausted all safe optimizations for this specific code structure.

The Math Boost: Adding -ffast-math drops the time from ~7537 ms to ~6266 ms. As the pdf with the lab instructions explains, this flag sacrifices strict floating-point precision for performance. Since the spin kernel relies heavily on expensive math functions, skipping strict IEEE rules yields a massive speedup.

2.2.1 - compute_color_simd_v0
Here is a visual map of exactly what we want in simd_v0:
1. THE VECTOR REGISTERS (What we started with)
 r_i: [ i0 | i1 | i2 | i3 | i4 | ... | i15 ]  (One massive 512-bit register)
 r_j: [ j0 | j1 | j2 | j3 | j4 | ... | j15 ]  (One massive 512-bit register)
          |    |    |    |    |          |
          v    v    v    v    v          v
 2. THE UNPACKING (Your pointer casting)
 ptr_i: i0, i1, i2... (Spilled out into standard memory)
 ptr_j: j0, j1, j2... (Spilled out into standard memory)
          |    |    |    |    |          |
          v    v    v    v    v          v
 3. THE BOTTLENECK (Your sequential loop)
        (16 separate, slow trips through compute_color_approx)
          |    |    |    |    |          |
          v    v    v    v    v          v
 4. THE PACKING (Your _mm512_loadu_epi32)
       [ c0 | c1 | c2 | c3 | c4 | ... | c15 ] (Crammed back into one register)

2.3.1 - fmodf_approx_simd
static inline __m512 fmodf_approx_simd(__m512 r_x, __m512 r_y) {
    __m512 r_div = _mm512_div_ps(r_x, r_y);
    __m512 r_trunc = _mm512_roundscale_ps(r_div, _MM_FROUND_TO_ZERO);
    __m512 r_mul = _mm512_mul_ps(r_trunc, r_y);
    return _mm512_sub_ps(r_x, r_mul);
}

static inline __m512i compute_color_simd_v1(__m512i r_i, __m512i r_j) {
    int32_t* ptr_i = (int32_t*)&r_i;
    int32_t* ptr_j = (int32_t*)&r_j;
    
    float temp_angles[16];
    float temp_ratios[16];
    int32_t temp_out[16];

    // Sequential math up to angle
    for (int k = 0; k < 16; k++) {
        float atan2f_in1 = (float)DIM / 2.f - (float)ptr_i[k];
        float atan2f_in2 = (float)ptr_j[k] - (float)DIM / 2.f;
        temp_angles[k] = atan2f_approx(atan2f_in1, atan2f_in2) + M_PIsp + base_angle;
    }

    // SIMD MATH: fmodf and ratio (all 16 at once!)
    __m512 r_angle = _mm512_loadu_ps(temp_angles);
    __m512 r_pi_4  = _mm512_set1_ps(M_PIsp / 4.f);
    __m512 r_pi_8  = _mm512_set1_ps(M_PIsp / 8.f);

    __m512 r_fmod  = fmodf_approx_simd(r_angle, r_pi_4);
    __m512 r_sub   = _mm512_sub_ps(r_fmod, r_pi_8);
    __m512 r_div   = _mm512_div_ps(r_sub, r_pi_8);
    __m512 r_ratio = _mm512_abs_ps(r_div); // SIMD version of fabsf

    _mm512_storeu_ps(temp_ratios, r_ratio); // Save ratios back to memory

    // Sequential color packing
    for (int k = 0; k < 16; k++) {
        float ratio = temp_ratios[k];
        uint32_t r = blue_r + (yellow_r - blue_r) * ratio;
        uint32_t g = blue_g + (yellow_g - blue_g) * ratio;
        uint32_t b = blue_b + (yellow_b - blue_b) * ratio;
        uint32_t a = blue_a + (yellow_a - blue_a) * ratio;
        temp_out[k] = ezv_rgba(r, g, b, a);
    }

    return _mm512_loadu_epi32(temp_out);
}
---

This code compiles BUT the compiler is warning us because we did something dangerous in C: we took a hardware vector register (r_i) and forcibly cast it into a standard memory pointer (int32_t*)&r_i.

If you look at the "PACC - Parallelism and Accelerators for Cluster Computing" document you provided, specifically on the "Intrinsics – Display for Debug" page, the teacher explicitly warns against this:uint8_t* T = (uint8_t*)ri8_512; // cast a register into an address, FORBIDDEN!!

So, we add

    // 1. Create standard arrays to hold the data
    int32_t temp_i[16];
    int32_t temp_j[16];

    // 2. Safely store the vector registers into those arrays
    _mm512_storeu_epi32(temp_i, r_i);
    _mm512_storeu_epi32(temp_j, r_j);

at the top of both compute_color_simd_v0 and compute_color_simd_v1 with this proper storage method.

    int32_t temp_i[16];
    int32_t temp_j[16];

    _mm512_storeu_epi32(temp_i, r_i);
    _mm512_storeu_epi32(temp_j, r_j);
    
    float temp_angles[16];
    float temp_ratios[16];
    int32_t temp_out[16];

    // 1. LOOP 1: Sequential math up to 'angle'
    for (int k = 0; k < 16; k++) {
        float atan2f_in1 = (float)DIM / 2.f - (float)temp_i[k];
        float atan2f_in2 = (float)temp_j[k] - (float)DIM / 2.f;
        temp_angles[k] = atan2f_approx(atan2f_in1, atan2f_in2) + M_PIsp + base_angle;
    }

    // 2. SIMD MATH: fmodf and ratio (all 16 at once!)

    __m512 r_pi_4  = _mm512_set1_ps(M_PIsp / 4.f);
    __m512 r_pi_8  = _mm512_set1_ps(M_PIsp / 8.f);

The execution time of ~393 ms is actually slightly higher than our 2-order unroll (~385 ms).
This is a perfect example of a hardware limit called register spilling. An AVX-512 CPU has exactly 32 vector registers available. By unrolling 4 times and trying to compute 64 pixels at once with all those intermediate variables, our code required more registers than the hardware physically possesses. The CPU was forced to temporarily "spill" data out to slower cache memory during the loop, which canceled out the speed benefits of unrolling. The 2-order unroll was the "sweet spot" for this specific processor.
